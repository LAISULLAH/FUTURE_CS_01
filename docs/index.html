Security Observation

The passive assessment of http://localhost:3000 revealed multiple security misconfigurations.

A critical Open Redirect vulnerability was identified exposing users to phishing. Missing security headers (CSP, X-Frame-Options) broaden the attack surface significantly. The CORS policy is overly permissive, allowing cross-domain data access.

Immediate remediation is recommended for High severity findings before any production exposure.

Assessment Context

Prepared By:L. Bloch

The internship task required performing a security assessment against a live web application. Conducting security scans against random public websites without explicit authorization is unethical and may violate organizational policies or applicable laws.

To ensure that the assessment was performed in a safe, legal, and Authorized Testing manner, OWASP Juice Shop was selected as the target application. OWASP Juice Shop is an intentionally vulnerable web application specifically designed for cybersecurity education, penetration testing practice, and security research.

For this assessment, OWASP Juice Shop was deployed and executed locally at http://localhost:3000 within a Local Test Environment. This approach provided a live, fully functional web application while ensuring that all testing remained authorized, isolated, and compliant with ethical security testing practices.

    1. http://localhost:3000 (1)
      1. Off-site Redirect (1)
        1. GET http://localhost:3000/redirect?to=https://github.com/juice-shop/juice-shop
          Alert Tags
          • OWASP_2025_A05
          • OWASP_2021_A03
          • WSTG-v42-CLNT-04
          • CWE-601
          • POLICY_QA_STD
          • POLICY_PENTEST
          • OWASP_2017_A01
          • POLICY_DEV_STD
          Alert Description

          Open redirects are one of the OWASP 2010 Top Ten vulnerabilities. This check looks at user-supplied input in query string parameters and POST data to identify where open redirects might be possible. Open redirects occur when an application allows user-supplied input (e.g. https://nottrusted.com) to control an off-site destination. This is generally a pretty accurate way to find where 301 or 302 redirects could be exploited by spammers or phishing attacks.

          For example an attacker could supply a user with the following link: https://example.com/example.php?url=https://malicious.example.com.

          NOTE: For the purposes of the passive check the authority portion of the origin and destination were compared. Manual testing may be required to validate the impact of this finding.
          Other Info

  2. MEDIUM

    Risk=Medium, Confidence=High (2)

    1. http://localhost:3000 (2)
      1. Content Security Policy (CSP) Header Not Set (1)
        1. GET http://localhost:3000/
          Alert Tags
          • OWASP_2021_A05
          • POLICY_QA_STD
          • POLICY_PENTEST
          • SYSTEMIC
          • CWE-693
          • OWASP_2017_A06
          Alert Description

          Content Security Policy (CSP) is an added layer of security that helps to detect and mitigate certain types of attacks, including Cross Site Scripting (XSS) and data injection attacks. These attacks are used for everything from data theft to site defacement or distribution of malware. CSP provides a set of standard HTTP headers that allow website owners to declare approved sources of content that browsers should be allowed to load on that page — covered types are JavaScript, CSS, HTML frames, fonts, images and embeddable objects such as Java applets, ActiveX, audio and video files.
          Solution

          Ensure that your web server, application server, load balancer, etc. is configured to set the Content-Security-Policy header.
      2. Cross-Domain Misconfiguration (1)
        1. GET http://localhost:3000/
          Alert Tags
          • OWASP_2017_A06
          • OWASP_2021_A05
          • CWE-264
          Alert Description

          Web browser data loading may be possible, due to a Cross Origin Resource Sharing (CORS) misconfiguration on the web server. The vulnerability has been confirmed by verifying that the server responds with an Access-Control-Allow-Origin header that permits any origin. While this is generally considered not to be a vulnerability on its own, it does allow for cross-domain resource sharing with any site.
          Solution

          Ensure that sensitive data is not available in an unauthenticated manner (using IP address white-listing, for instance). Configure the "Access-Control-Allow-Origin" HTTP header to a more restrictive set of domains, or remove all CORS headers entirely, to allow the web browser to enforce the Same Origin Policy (SOP) in a more restrictive manner.
  3. MEDIUM

    Risk=Medium, Confidence=Medium (2)

    1. http://localhost:3000 (2)
      1. Missing Anti-clickjacking Header (1)
        1. GET http://localhost:3000/
          Alert Description

          The response does not include either Content-Security-Policy with 'frame-ancestors' directive or X-Frame-Options to protect against 'ClickJacking' attacks.
          Solution

          Modern Web browsers support the Content-Security-Policy and X-Frame-Options HTTP headers. Ensure one of them is set on all web pages returned by your site/app. If you expect the page to be framed only by pages on your server then use SAMEORIGIN, otherwise if you never expect the page to be framed, you should use DENY. Alternatively consider implementing Content Security Policy's "frame-ancestors" directive.
      2. Session ID in URL Rewrite (1)
        1. GET http://localhost:3000/
          Alert Description

          URL rewrite is used to track user sessions, which can lead to session fixation attacks, and make it easier for attackers to capture session tokens. The session ID was found in the URL.
          Solution

          For secure session management, it is strongly recommended to: (1) Use cookies for session token transmission. (2) Implement Secure and HttpOnly cookie flags. (3) Use strong session ID generation. (4) Implement proper session invalidation.
  4. LOW

    Risk=Low, Confidence=Medium (2)

    1. http://localhost:3000 (2)
      1. Timestamp Disclosure - Unix (1)
        1. GET http://localhost:3000/
          Alert Description

          A timestamp was disclosed by the application/web server. Information about internal server clock may aid an attacker in identifying software versions, etc.

          Solution

          Manually confirm that the timestamp data is not sensitive, and that the data cannot be aggregated to disclose exploitable patterns.

      2. X-Content-Type-Options Header Missing (1)
        1. GET http://localhost:3000/
          Alert Description

          The Anti-MIME-Sniffing header X-Content-Type-Options was not set to 'nosniff'. This allows older versions of Internet Explorer and Chrome to perform MIME-sniffing on the response body, potentially causing the response body to be interpreted and displayed as a content type other than the declared content type.

          Solution

          Ensure that the application/web server sets the Content-Type header appropriately, and that it sets the X-Content-Type-Options header to 'nosniff' for all web pages.

  5. LOW

    Risk=Low, Confidence=Low (1)

    1. http://localhost:3000 (1)
      1. Private IP Disclosure (1)
        1. GET http://localhost:3000/
          Alert Description

          A private IP (such as 10.x.x.x, 172.x.x.x, 192.168.x.x) or an Amazon EC2 private hostname (for example, ip-10-0-56-78) has been found in the HTTP response body. This information might be helpful for a more targeted attack against the internal systems.

Recommendations

The following remediation actions are recommended in order of priority. All high severity findings should be addressed before the application is exposed to production traffic.

P1

Fix Open Redirect Vulnerability

Validate and whitelist allowed redirect destinations. Reject any redirect to off-site URLs that are not in an approved list. Affects CWE-601.

Critical Priority
P2

Implement Content Security Policy

Add a strict CSP header to all responses. Configure Content-Security-Policy to restrict allowed sources for scripts, styles, and frames.

High Priority
P3

Restrict CORS Policy

Replace wildcard Access-Control-Allow-Origin: * with an explicit whitelist of trusted domains to prevent unauthorized cross-domain data access.

High Priority
P4

Add X-Frame-Options Header

Set X-Frame-Options: DENY or SAMEORIGIN on all pages to prevent clickjacking attacks.

Medium Priority
P5

Migrate Session Tokens to Cookies

Stop passing session tokens via URL parameters. Use HttpOnly; Secure; SameSite=Strict cookies to prevent session hijacking and fixation.

Medium Priority
P6

Add X-Content-Type-Options Header

Set X-Content-Type-Options: nosniff on all responses to prevent MIME type sniffing attacks in legacy browsers.

Low Priority
